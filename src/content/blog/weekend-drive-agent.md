주말마다 같은 일을 반복하고 있었습니다. 지도 앱을 열어 안 막히는 길을 찾고, 주유소에서 계기판 연비를 눈으로 확인하고, 다음 주에 또 처음부터.
그래서 **코스 탐색과 연비 기록을 한 장으로 합친 웹페이지**를 만들었습니다.

결과물은 HTML 파일 하나입니다. 빌드 단계가 없고, 열면 아무것도 입력하지 않아도 추천 코스가 지도 위에 그려집니다.

## 요구사항은 네 줄이었다

처음 적은 것은 이 정도였습니다.

- 주말에 안 막히는 코스를 추천해 줄 것
- 예상 연비를 계산해 줄 것
- 지도 위에 경로가 직접 그려질 것
- 5초 안에 뜰 것

읽으면 명확해 보이는데, 코드를 쓰려고 하면 한 줄도 진행되지 않습니다. **"안 막히는"이 몇 퍼센트인지, 그걸 누가 판정하는지가 없기 때문입니다.**

그래서 코드보다 스펙을 먼저 썼습니다. 이 글은 그 과정에서 드러난 구멍들의 기록입니다.

## 구멍 1 — 판단은 누가 하는가

"정체율이 낮은 경로를 추천한다"고 적어 놓고 보니, 그 판단의 주체가 없었습니다. 지도 API인지, LLM인지, 코드인지.

네 계층으로 쪼갰습니다.

| 계층 | 주체 | 역할 | 판단 권한 |
| --- | --- | --- | --- |
| 데이터 | 지도 API | 구간별 실시간 속도 제공 | 없음 (원자료만) |
| 판정 | **규칙 기반 코드** | 정체율 산출 → 필터 → 점수 → 순위 | **있음** |
| 설명 | LLM | 선정 이유를 한 줄로 요약 | 없음 (경로를 못 바꿈) |
| 결정 | 사용자 | 수용 또는 목적지 직접 지정 | 있음 (최상위) |

경로 선택을 LLM에 맡기지 않은 이유는 하나입니다. **검증 기준을 합격·불합격으로 쓰려면 같은 입력에 같은 답이 나와야 합니다.** "정체 구간 비율 8% 미만"을 테스트로 만들려면 판정이 재현 가능해야 하고, LLM은 그걸 보장하지 않습니다.

LLM은 이미 정해진 결과를 설명하는 자리로 내려보냈습니다.

## 구멍 2 — "정체율이 낮다"는 순위가 아니다

정체율만으로는 순위가 정해지지 않습니다. 정체율 3% · 편도 90km 코스와 정체율 7% · 편도 40km 코스 중 무엇이 나은지 판단할 근거가 없습니다.

가중합으로 점수를 냈습니다.

```
score = w1 × (1 − 정체율)
      + w2 × 고속주행비율
      + w3 × (1 − 거리편차)

거리편차 = |코스 거리 − 선호 거리| ÷ 선호 거리
```

| 가중치 | 항목 | 값 |
| --- | --- | --- |
| `w1` | 정체 회피 | **0.5** |
| `w2` | 고속 주행 비율 | 0.3 |
| `w3` | 선호 거리 근접도 | 0.2 |

여기에 동점 처리도 필요했습니다. 점수 차가 0.02 이내면 정체율 → 예상 연비 → POI id 순으로 정합니다. 마지막 타이브레이커가 id인 이유는 **API 반환 순서에 의존하지 않기 위해서**입니다.

## 구멍 3 — 그건 언제의 정체율인가

가장 오래 붙잡은 문제입니다. 실시간 교통은 **조회한 그 순간**의 값인데, 편도 40km만 달려도 도착은 40분 뒤이고 왕복이면 귀로는 세 시간 뒤입니다.

시점을 네 개로 나눴습니다.

| 시점 | 언제 | 소스 | 신뢰도 |
| --- | --- | --- | --- |
| T0 출발 | 조회 즉시 | 실시간 교통 | 높음 |
| T1 도착 | T0 + 편도 소요 | 실시간 + 통계 보정 | 중간 |
| T2 귀가 출발 | T1 + 체류 시간 | 시간대별 통계 | 낮음 |
| T3 귀가 도착 | T2 + 귀로 소요 | 시간대별 통계 | 낮음 |

그리고 경로를 소요 시간 순으로 잘라, 각 조각이 **실제로 통과할 시각**의 데이터를 씁니다.

```
구간 i 정체율 = α × 실시간(i) + (1 − α) × 통계(i, 통과 예정 시각)
α = max(0, 1 − 통과까지 남은 시간 ÷ 90분)
```

30분 안에 통과할 구간은 실시간을 2/3 비중으로 쓰고, 90분 이후 구간은 통계만 씁니다. 귀로는 α가 0이 되어 사실상 통계 기반입니다.

여기서 판정 범위를 좁히는 결정을 했습니다. **합격·불합격은 편도만 봅니다.** 귀로는 통계 예측이라 사후 실측과 어긋날 수 있어 기준으로 쓸 수 없습니다. 대신 화면에는 범위로 적습니다.

> 귀로 예상 정체 11% ~ 19% (예측)

단일 숫자로 적으면 사용자가 예측을 사실로 받아들입니다. 지도에서도 예측 구간은 실선이 아니라 **점선 + 반투명**으로 그립니다.

## 구멍 4 — 편도인가 왕복인가

"편도 60km 코스"라고 적어 놓고, 연비도 편도 기준으로 계산하고 있었습니다.

그런데 검증 기준은 `예상 연비 vs 계기판 연비 ±1.0km/L`입니다. **계기판 연비는 왕복 주행을 마친 뒤 읽는 값입니다.** 축이 달랐습니다.

거리 표기 규칙을 문서에 못 박고 산식을 고쳤습니다.

```
예상 연비 = 왕복 총 거리 ÷ Σ ( 구간 거리 ÷ 구간 연비 )
```

단순 산술평균이 아니라 **거리 가중 조화평균**입니다. 산술평균은 연비를 과대평가합니다. 100km를 20km/L로 달리고 100km를 10km/L로 달렸을 때 평균은 15km/L가 아니라 13.3km/L입니다.

## 고정 코스 풀을 버린 이유

처음에는 추천 코스 여섯 개를 문서에 표로 박아 뒀습니다. 서해안 노을, 강화 순환, 남한강 라인 같은 것들.

이게 두 가지를 동시에 깨뜨렸습니다. 사용자 위치와 무관하게 고정된 출발지를 쓰게 되고, 코스 품질이 제가 임의로 고른 여섯 개 안에 갇힙니다.

런타임 생성으로 바꿨습니다. 페이지에 들어온 시점에 출발지·목적지 쌍 아홉 개를 만들어 냅니다.

| 단계 | 하는 일 | 외부 호출 |
| --- | --- | --- |
| ① 출발지 확정 | 좌표를 100m 그리드로 스냅 | 없음 |
| ② 반경 밴드 | 선호 거리 ÷ 우회계수 | 없음 |
| ③ 후보 수집 | 밴드 안에서 카테고리별 POI 검색 | POI 1회 |
| ④ 선별 | 방위 분산 · 품질 · 중복 제거 → 9개 | 없음 |
| ⑤ 산출 | 성격 라벨, 대략 편도 거리 | 없음 |
| ⑥ 경로 탐색 | **상위 3개만** | 경로 3회 |

대신 재현성이 흔들립니다. 고정 풀이 없으면 "같은 입력에 같은 결과"가 성립하지 않습니다.

그래서 생성 결과를 해시해 `courseSetId`를 만들고 스냅샷으로 저장했습니다. 출발지 좌표를 100m 그리드로 반올림하는 것도 같은 이유입니다 — 같은 자리에서 새로고침하면 같은 후보 집합이 나와야 합니다.

**재현성의 기준선이 "코스 풀"에서 `courseSetId`로 옮겨간 것입니다.** 판정이 결정론적이라는 성질 자체는 그대로 남습니다.

## 지도에 선 긋기

경로는 이미지가 아니라 좌표 배열로 받아서 벡터로 그립니다. 정체 구간을 색으로 구분해야 하니 선 하나가 아니라 **등급이 바뀌는 지점에서 쪼갠 여러 개의 선**을 이어 붙입니다.

```js
function splitByTraffic(coords, levels) {
  const segments = [];
  let start = 0;
  for (let i = 1; i <= coords.length - 1; i++) {
    if (levels[i] !== levels[start] || i === coords.length - 1) {
      segments.push({ path: coords.slice(start, i + 1), level: levels[start] });
      start = i;              // 정점 1개를 공유
    }
  }
  return segments;
}
```

`start = i`에서 정점을 하나 공유하는 게 핵심입니다. 그냥 자르면 색이 바뀌는 지점마다 1픽셀 틈이 생겨 경로가 끊어져 보입니다. 처음에 `start = i + 1`로 써서 점선처럼 보이는 경로를 한참 들여다봤습니다.

## 유가 때문에 서버가 필요해졌다

"단일 파일"을 목표로 했는데, 기름값을 붙이려니 서버가 생겼습니다.

연비만 보여주면 "이 코스가 얼마짜리인지" 감이 안 옵니다. 왕복 기름값을 함께 내려면 유가가 필요하고, 유가 조회는 브라우저에서 직접 하면 CORS에 막힙니다.

그래서 파이썬 표준 라이브러리만으로 엔드포인트 하나를 얹었습니다.

```python
class Handler(http.server.SimpleHTTPRequestHandler):
    def do_GET(self):
        if self.path == '/api/fuel':
            # 전국 주유소 평균가를 조회해 JSON으로 돌려준다
            ...
            return
        return super().do_GET()
```

```bash
python3 server.py 4173
```

정적 서버로 열어도 페이지는 동작합니다. `/api/fuel`이 404가 나면 초기 단가로 고정될 뿐입니다. **값을 못 받았다고 기름값 칸을 비우지는 않습니다.**

"단일 파일"의 범위도 문서에 다시 적었습니다 — 산출물은 파일 하나, 네트워크 의존은 허용. 지도 타일과 실시간 교통은 런타임 호출이 필요하니 완전한 자기완결은 애초에 불가능합니다.

## 문서와 코드가 갈라진 자리

구현을 마치고 문서와 대조했더니, 문서가 앞서 있는 구간이 여덟 개 있었습니다.

| 항목 | 현재 상태 |
| --- | --- |
| LLM 설명 계층 | 규칙 기반 템플릿 문장으로 대체 |
| 경유지 정체율 상승 검증 | 예산 상수는 있으나 검사 코드가 없음 |
| L3 실측 보정 | 표본을 읽기만 하고 쓰는 경로가 없음 |
| 실연비 입력 | 공인연비 고정값만 사용 |
| 스냅샷 리플레이 | 저장만 하고 읽지 않음 |

이 중 세 개는 검증 기준을 직접 무력화합니다. 실연비 입력이 없으면 `±1.0km/L`를 잴 수 없고, 스냅샷을 읽지 않으면 리플레이 테스트가 성립하지 않습니다.

지우는 대신 **README에 「구현 현황」 절을 만들어 남겼습니다.** 의도적으로 다르게 만든 것, 아직 구현하지 않은 것, 알려진 결함을 나눠서 표로. 검증 기준 아래에는 "지금 측정 가능한 항목은 이것들"이라고 한 줄 붙였습니다.

문서가 코드를 실제보다 좋아 보이게 만드는 것이 가장 나쁜 경우라고 생각합니다.

## 남은 것

가장 마음에 걸리는 건 L2 계수 테이블입니다. 4개 도로 등급 × 6개 시간대 = 24개 값으로 주말 교통량을 근사하는데, 이 값들이 전부 제 가정입니다. 공공 소통정보 이력으로 한 번 실측 검증해야 합니다.

경유지 우회 시간을 직선거리로 근사한 것도 그렇습니다. 경로를 재탐색해서 재는 게 맞지만 API 호출이 슬롯당 세 배로 늘어납니다. 쿼터와 정확도를 맞바꾼 셈인데, 아직 어느 쪽이 옳은지 모르겠습니다.

> 스펙을 먼저 쓰면 코드가 빨라지는 게 아니라, **질문이 빨라집니다.** "안 막히는 코스"라는 네 글자에서 판단 주체, 시간축, 거리 기준, 재현성 네 개의 질문이 나왔고, 코드를 먼저 썼다면 넷 다 나중에 만났을 겁니다.
